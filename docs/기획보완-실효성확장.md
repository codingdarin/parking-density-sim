# 기획 보완 — 실효성 확장 (Phase 2 기획)

**상태**: v1 (2026-07-30)
**위치**: [개발계획서](./개발계획서.md)는 동결 상태이므로 본 문서가 Phase 2(실효성 확장)의 기준 문서가 된다. 기존 문서의 용어(α, β, 순이득, 핵심 스위치, FMS 트리거)를 그대로 계승한다.
**한 줄 요약**: 연구 장치는 완성됐다. 이제 이 장치를 **누가·언제·왜 쓰는지**를 정의하고, 정적 설계 질문을 동적 운영 질문으로 확장한다.

## 1부. 진단 — 왜 목표성·유용성이 흐려졌는가

### 1-1. 잘된 것 (보유 자산)

이 프로젝트의 자산은 코드보다 **방법론적 규율**에 있다. 확장 기획에서도 이 규율을 그대로 적용한다.

| 자산 | 내용 | Phase 2에서의 의미 |
|---|---|---|
| 사전예측/결과 쌍 기록 | 모든 작업이 예측 고정 → 실측 대조로 기록됨 (작업일지 130여 섹션) | 새 기능도 같은 형식으로 — 예측-실측 격차 자체가 발표 자료 |
| 검증 게이트 | V2 타당성 게이트 62종 + V1 뮤테이션 테스트 (예약 끄면 전부 실패해야 정상) | 배터리·교란 등 새 메커니즘도 게이트 추가 방식으로 편입 |
| Core 순수성 가드 | ConsoleSim 빌드가 Unity 비의존의 컴파일 타임 가드 | 새 운영 로직도 콘솔에서 먼저 개발·검증 가능 |
| 지적 정직성 | V1 정량 결과를 스스로 무효 선언하고 V2 재구축 | 서사의 약점이 아니라 강점 — 숨기지 말 것 |
| Unity 표현 계층 | 관제모드/3D모드 분리, 추적 카메라, 화재동 선택, 밀도 조작, 5/7/9분 판정 UI, Windows 플레이어 빌드 | **관제보드 제품의 뼈대가 이미 있다** — 새로 만드는 게 아니라 용도를 부여하는 것 |

### 1-2. 흐려진 구조적 원인 — "연구 장치는 있는데 사용자가 없다"

현재 시뮬레이터가 답하는 질문은 하나다:

> "이 밀도 정책은 안전한가?" (설계 시점, 배치 실험, 답은 CSV 23개 + 리포트 1개)

이 질문의 수요자는 사실상 연구자 본인뿐이다. 기획정의서가 약속한 "선택의 대가를 숫자로 보여주는 도구"는 **의사결정자가 도구를 만질 때** 성립하는데, 현재 산출물 형태(CSV·콘솔 커맨드 36종)는 만질 수 있는 사람이 없다. 구체적으로:

1. **핵심 스위치 미조립** — 기획정의서 §6의 α↔N 교환비 표가 최종 산출물로 조립된 적이 없다. 조각(미보정 안전거리, 순α 회계, 속도 민감도)은 `output/v2_report.md`에 다 있는데 "몇 대를 더 받고 몇 초를 잃는가" 한 장이 없다.
2. **헤드라인 분산** — V1 무효 → V2 재구축 과정에서 산출물이 스윕 단위(안전 도달거리 / 연속 8동 안전 최대 N / net α)로 파편화됐고, 무엇이 대표 결론인지 문서 간 합의가 없다.
3. **운영 시점 질문의 부재** — "지금 이 순간 불이 나면 대응 가능한가?"라는 질문을 다루지 않는다. 실제 로봇 주차장의 안전 논증은 설계 승인으로 끝나지 않고 **상시 운영 상태**(로봇 가용성, 배터리, 통로 상태)에 의존하는데, 모델에 운영 상태라는 개념 자체가 없다. 이것이 사용자가 느낀 "실효성 부족"의 핵심이다.
4. **범위 관성** — 최근 커밋 약 30건이 전부 시각 폴리시. D10 이후라 규칙 위반은 아니지만, 연구 질문이 전진하지 않는 구간이 길어지며 방향 감각이 흐려졌다.

## 2부. 페르소나와 사용 시나리오 — 제품 관점 재정의

도구가 답해야 할 질문을 사람 기준으로 다시 세운다. 세 페르소나는 같은 시뮬레이션 코어를 서로 다른 화면·시점으로 소비한다.

### P1. 아파트 관리사무소 방재 담당자 — 관제보드

| 항목 | 정의 |
|---|---|
| 핵심 질문 | **"지금 불나면 우리 단지는 몇 분 만에 열리나?"** |
| 사용 시점 | 상시 (모니터링) + 비상시 (대응 확인·수동 개입) |
| 보는 화면 | 현 관제모드를 재편한 **관제보드**: 단지 평면 + 동별 실시간 대응력 게이지("101동 4.2분 / 108동 6.8분") + 화재 발생 시 선택 경로·개통 진행률·잔여 시간 표시 |
| 필요한 신규 개념 | **상시 대응력 지표** — 현재 점유·로봇 상태를 입력으로 8개 동 예상 개통시간을 백그라운드 재계산. 지금은 화재를 지정해야 계산이 시작되지만, 관제보드는 화재가 나기 전에 항상 답을 들고 있어야 한다 |
| 근거 연결 | 측정정의서 §2의 FMS 트리거(119 신고 연동, 수동 트리거는 보조)가 이 페르소나의 개입 지점을 이미 정의해 두었다 |

이 페르소나가 Phase 2의 중심이다. 기존 관제모드 UI 자산을 그대로 승격시킬 수 있어 비용 대비 효과가 가장 크고, "이 화면이 관리사무소 벽에 걸려 있다"는 그림 하나로 도구의 존재 이유가 즉시 전달된다.

### P2. 주차로봇 운영사 FMS 오퍼레이터 — 평시 운영 모드

| 항목 | 정의 |
|---|---|
| 핵심 질문 | **"로봇 함대가 지금 비상 대응 가능한 상태인가?"** |
| 사용 시점 | 상시 (함대 관리) |
| 보는 화면 | 로봇별 배터리·상태(대기/운반/충전/고장)·작업 큐, **비상 대응 가용 로봇 수** 게이지 |
| 필요한 신규 개념 | 배터리·충전 스테이션·핸드오버 모델 (3부 R1). "로봇 4대 보유"와 "지금 비상 투입 가능 4대"는 다르다 — 이 간극이 P2의 존재 이유 |
| 근거 연결 | 재배치 규칙 9("필요한 조만 활성화")가 이미 함대 부분 활성화 개념을 도입해 두었다 |

### P3. 성능위주설계 심의자·사업 검토자 — 근거 계층 (기존 자산)

| 항목 | 정의 |
|---|---|
| 핵심 질문 | **"이 밀도 정책은 안전한가? 근거는?"** |
| 사용 시점 | 설계·심의 시점 (1회성) |
| 보는 화면 | 배치 실험 CSV·자동 리포트 — **이미 존재.** 추가할 것은 핵심 스위치 1장 조립(3부 R5)뿐 |
| 역할 | P1·P2 화면에 표시되는 모든 숫자의 검증 근거. 관제보드가 "4.2분"이라고 말할 수 있는 이유가 이 계층이다 |

**세 페르소나의 관계**: P3(설계 근거) → P1(상시 확인) → P2(가용성 유지). 정적 안전 논증이 동적 운영 보증으로 이어지는 구조이며, 이것이 "시뮬레이터"가 "관제 시스템의 디지털 트윈 프로토타입"으로 승격되는 서사다. 포트폴리오 관점에서는 "연구를 했다"에서 "**연구 결과로 제품을 정의했다**"로 이야기가 한 단계 올라간다.

## 3부. 운영 리얼리즘 로드맵

우선순위 순. 각 항목에 비용(소/중/대)·효과·완료 기준을 병기한다. 공통 원칙: **모든 새 메커니즘은 Core(순수 C#)에서 콘솔로 먼저 검증하고 게이트를 추가한 뒤 Unity에 표현을 얹는다** — 기존 개발 규율 그대로.

### R1. 배터리·충전·핸드오버 (비용 중 / 효과 대) — P2의 기반

- **모델**: 로봇별 배터리 상태(틱당 소모: 주행/적재 주행/대기 차등) + 충전 스테이션(적치 구역처럼 1급 레이아웃 요소, 위치·구수 파라미터) + 임계치 도달 시 충전 복귀. 소모율·충전율은 Stanley 공개사양 참조 프로파일과 미보정 기준선의 2단 구성 — 기존 `PhysicalTimeProfileV2` 패턴 재사용.
- **핸드오버**: 작업 중 로봇이 임계치에 걸리면 대체 로봇이 남은 작업을 **재계획으로 승계**. 승계 시점의 차량 위치에서 새 최적경로를 계산하므로 기존 MAPF 스택(예약 테이블·우선순위 재시도)이 그대로 시험대가 된다.
- **신규 지표**: 비상 대응 가용 로봇 수(배터리 제약 반영), 핸드오버 지연(승계로 늘어난 개통시간), **충전 정책별 7분 보장 붕괴 지점** — 핵심 스위치의 운영 버전. "α↔N 교환비"가 "충전 여유↔대응력 교환비"로 확장된다.
- **완료 기준**: 콘솔 시나리오에서 배터리 부족 → 충전 복귀 → 대체 승계 → 개통 완료가 결정론적으로 재현(시드 고정). 게이트 추가: 배터리 보존(소모=충전+잔량 회계), 핸드오버 전후 계획 유효성, 재현성.

### R2. 교란 이벤트 주입 (비용 소 / 효과 대) — 회복탄력성 지표

- **모델**: 시뮬레이션 도중 임의 틱에 주입되는 이벤트 3종 — ① 셀 봉쇄(쓰러진 나무·낙하물: floor 셀 집합을 주행 불가로 전환) ② 로봇 고장(즉시 이탈, R1의 핸드오버로 승계) ③ 비관리 차량(로봇이 옮길 수 없는 고정 장애물 — 기존 `FixedObstruction` 실패 사유가 이미 이 개념을 알고 있다).
- **핵심 산출물**: **회복탄력성 곡선** — 교란 발생 시점·위치를 스윕해 "재계획 후에도 7분이 유지되는가"를 집계. 밀도 N이 높을수록 우회 여유가 없어 교란에 취약해진다는 가설 검증 → 정적 안전 최대 N과 **교란 하 안전 최대 N**의 격차가 새 헤드라인.
- **왜 효과 대인가**: 경로가 막혔을 때 전 함대가 실시간으로 재계획해 우회하는 장면은 MAPF 스택의 능력을 보여주는 최고의 데모이고, 구현은 대부분 기존 코드(봉쇄 = floor 수정 후 재계획 호출)로 성립한다.
- **완료 기준**: 교란 시점×위치 스윕 CSV + 콘솔 재현 시나리오 1종. 게이트 추가: 교란 후 재계획 해의 무충돌성, 해 없음 시 "확보 실패" 정상 종료(기존 테스트 ⑤ 패턴).

### R3. 실제 타겟 단지 1건 적용 (비용 중 / 효과 대) — "실제 이용 가능한 타겟"

- **내용**: 합성 8동 단지를 유지하되, 실제 아파트 단지 1곳의 공개 배치도(단지 안내도·위성 사진 기반)를 격자로 옮긴 레이아웃을 추가한다. 동 배치·도로 폭·진입구 수를 실물 기준으로 잡고 전체 스윕(밀도·강건성·교란)을 재실행.
- **의미**: 측정정의서 한계 §11("실제 총세대수와 사업승인 도면에 따라 별도 생성 필요")에 대한 직접 응답. "합성 격자 결과"라는 해석 제한 하나가 지워지고, 관제보드(P1)에 실존 단지 이름이 올라간다.
- **주의**: 특정 단지 실명 공개 시 "이 단지는 위험하다" 식 서술이 되지 않도록 익명화(단지 A) 또는 허가 확인. 측정정의서의 윤리 서술 원칙(§2 임계값 민감도의 서술 금지 조항)과 같은 결의 문제.
- **완료 기준**: 실측 레이아웃 팩토리 1종 + 8동 합성 대비 동일 지표 비교표.

### R4. 도로 기하 현실화 (비용 대 / **신중 권고 — 전면 연속화 비권고**)

- **요구의 본질**: "반듯한 격자가 아니라 실제 도로의 곡률" — 정당한 지적이지만, 격자 이산화는 이 프로젝트의 계산 기반(예약 테이블, BFS 정확해 오라클, 62 게이트 전부)이다. 연속 공간 전환은 사실상 재작성이며, V1→V2 재구축을 이미 한 번 치른 프로젝트에 두 번째 재작성을 권하지 않는다.
- **권고안 — 2단계 근사**: ① **표현 계층 스무딩**: Unity에서 격자 경로를 스플라인으로 보간해 주행 표현만 연속화 (Core 불변, 관제보드·3D 인상 개선) ② **swept-volume 검증 후처리**: 곡선 구간에서 1×2 강체의 스윕 면적이 폭 3셀 경로를 실제로 벗어나지 않는지 사후 검증 지표를 추가 — "격자 근사가 곡률을 감췄는가"라는 방법론적 질문에 정량 답변이 생기고, 기획정의서 한계 §11("연속 공간 자유주행 근사")이 검증된 한계로 승격된다.
- **완료 기준**: ①은 표현 계층 커밋, ②는 검증 리포트 1종. 곡률 반영 신규 레이아웃(곡선 도로 단지)은 R3 실측 단지에 곡선 구간이 있을 때만 격자 해상도 세분화(예: 1.25m 셀)로 대응 검토.

### R5. 핵심 스위치 최종 조립 (비용 소 / 효과 대) — P3 완결

- **내용**: 기획정의서 §6 표를 실측으로 채운 **최종 트레이드오프 1장**: x축 밀도(N), y축 개통시간, 5/7/9분 밴드, net α 회계(순이득 조건 명시), 봉투 이차 예측선 vs 실측 곡선 오버레이(변곡점 = 시뮬레이터의 존재 증명). 헤드라인 문장 형식: "α대를 더 받으면 최악 화재 기준 N초를 잃는다 — 단, α대분의 비주차 포장 공간이 조건이다."
- **의미**: 신규 실험이 아니라 기존 CSV의 조립. Phase 2 어떤 항목보다 먼저 끝낼 수 있고, 이후 R1·R2가 이 1장에 "운영 열"(교란 하/배터리 제약 하)을 추가하는 구조가 된다.
- **완료 기준**: `output/`에 최종 표·곡선 생성 + README 최상단을 이 결론으로 재구성.

## 4부. 실행 순서 제안 (Phase 2 스프린트)

D-일차 체계와 별도의 Phase 2 체계. 각 스프린트는 기존 규율(사전예측 → 구현 → 실측 → 게이트 → 작업일지) 그대로 진행하며, **코드 착수는 사용자 지시가 있는 사이클부터**.

| 스프린트 | 내용 | 근거 |
|---|---|---|
| **S0** | R5 핵심 스위치 조립 + 코드 백로그 1~3번 (Runner 분해·상수 단일화·CSV 재현성) | 신규 실험 없이 목표성 즉시 복원 + R1 이후를 위한 지반 정리 |
| **S1** | R2 교란 이벤트 (Core → 콘솔 → 게이트) | 최소 비용으로 "동적 운영" 첫 진입, 회복탄력성 지표 확보 |
| **S2** | R1 배터리·충전·핸드오버 (Core → 콘솔 → 게이트) | P2 성립, 핸드오버가 R2의 로봇 고장과 접합 |
| **S3** | P1 관제보드 모드 (Unity — 상시 대응력 게이지·교란/배터리 표시) | S1·S2의 지표를 화면으로. Runner 분해(S0) 후라 안전 |
| **S4** | R3 실측 단지 적용 → 전체 스윕 재실행 | 실효성 최종 증명, R4-② swept 검증 병행 |

**Phase 2가 끝났을 때의 한 줄**:

> "밀도 정책의 안전을 설계 시점에 증명하고(P3), 그 보증이 운영 중에도 유지되는지 상시 감시하는(P1·P2) 로봇 주차장 관제 시뮬레이터 — 실측 단지 1건에서 교란·배터리 제약까지 검증."
