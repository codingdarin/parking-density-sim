# parking-density-sim

로봇 주차장이 평상시 통로를 점유해 얻는 추가 수용량과, 비상시 통로 확보에 드는 시간을 비교하는 시뮬레이터입니다.

핵심 질문은 하나입니다.

> 비상시 규정 폭을 7분 안에 확보할 수 있다면, 평상시 통로 점유를 어디까지 허용할 수 있는가?

## 결론 — 몇 대를 더 받고, 몇 초를 잃는가

폭3×100m 통로·운송 유닛 4조의 **미보정 알고리즘 기준선**(틱×2.5초, 현실 성능값
아님) 실측입니다. 전체 조립은 `dotnet run --project ConsoleSim -- v2switch`가
`output/v2_core_switch.md`로 생성합니다.

| 정책 | 수용 대수 (500면 기준) | 최악(최원단 100m) 확보 시간 | 7분 판정 |
|---|---:|---:|---|
| 현행 기준(상시 비움) | 500대 | 0초 | 통과 |
| 1레인 점유 | +20대 (+4%) | 13.7분 | 실패 |
| 2레인 점유 | +40대 (+8%) | 29.8분 | 실패 |
| 3레인 점유 | +60대 (+12%) | 49.6분 | 실패 |

- 어떤 점유 수준도 최원단 화재의 7분 확보를 만족하지 못합니다. 전 구간 7분은
  **분산 적치 포켓 처방**(1레인·포켓14 강건안, 400초)으로만 복원되며, 포켓 부지의
  주차 기회비용을 차감한 순이득은 **+6대(+1.2%)** 까지 줄어듭니다.
- 실측 7분 안전 도달거리(55/30/20m)는 봉투 이차 모델의 p=4 완전 병렬
  상한(65/40/30m)보다 레인별 10m 짧습니다 — 간섭·병렬성 붕괴의 크기는 봉투
  계산이 아니라 시뮬레이션이 답하는 값입니다
  (`output/v2_core_switch_curve.csv`, 60점 전 구간 실측/봉투 비율 ≥ 1).
- Stanley 공개사양(취득90초·해제60초)을 적용하면 서비스 시간이 지배해 위 통과
  판정도 뒤집힙니다 — 아래 현실 시간 민감도 참조.

## 현재 Model V2

- 차량은 소멸하지 않고 유한 적치면을 계속 점유합니다.
- 차량 pose는 1×2셀 가로/세로이며 운반 중 회전·충돌을 검사합니다.
- 운송 유닛 1~8조, 시공간 A* 정점/엣지 예약, 유한 적치 배정을 지원합니다.
- 입구와 화재 위치에서 폭 3셀 접근 후보를 상위 K개까지 자동 생성하고,
  후보별 물리 개통시간을 비교합니다.
- 적치 슬롯별 토지 성격을 기존 비주차 포장·주차 가능 부지 전용·미확인으로
  구분하고, 상시 전용한 전체 적치면의 기회비용을 순수용량에서 차감합니다.
- 소형 문제는 exact 오라클과 비교하고, 운영 규모는 bounded 후보의 물리 유효 상한으로 보고합니다.
- Core는 Unity 비의존 순수 C#이며 ConsoleSim과 Unity가 같은 구현을 사용합니다.

## 핵심 결과

아래 표는 폭3×100m 통로, 이동1m/s, pickup/drop 각1틱, 운송 유닛4조의
**미보정 알고리즘 기준선**입니다. 단순 `틱×2.5초`는 현실 성능값이 아닙니다.

| 점유 레인 | 추가 수용량 | 7분 안전 도달거리 | 100m 확보시간 |
|---:|---:|---:|---:|
| 1 | +20대 (+4%) | 55m | 329틱 / 13.7분 |
| 2 | +40대 (+8%) | 30m | 716틱 / 29.8분 |
| 3 | +60대 (+12%) | 20m | 1,190틱 / 49.6분 |

미보정 기준에서는 1레인·100m 포켓14가 160틱(400초)으로 7분을
만족합니다. 다만 포켓의 주차 기회비용을 빼면 순증가 수용량은
+6대(+1.2%)로 감소합니다.

[Stanley Robotics 공개 기술사양](https://www.stanley-robotics.com/wp-content/uploads/2022/07/stanley-robotics-robot-spec.pdf)의
차량 취득90초·해제60초를 적용하면 결론이 달라집니다.

| 이동속도 | 상시개방 | 전면5대 | 상부2대 | 자동 하부3대 | 포켓14·20대 |
|---:|---:|---:|---:|---:|---:|
| 1m/s | 0초 | 432.5초(실패) | 242.5초 | 235.0초 | 1,102.5초(실패) |
| 2m/s | 0초 | 366.2초 | 196.2초 | 192.5초 | 977.5초(실패) |
| 3m/s(공개 최대) | 0초 | 344.2초 | 180.8초 | 178.3초 | 901.7초(실패) |

차량20대/4조는 pickup+drop 서비스만 최소 750초이므로 이동속도와 무관하게
7분을 넘습니다. 따라서 160틱 통과는 알고리즘 회귀값으로만 유지합니다.
같은 지상형 맵에서는 자동 하부가 전면 재배치보다 45.7~48.2% 빠르고,
차량 수가 더 적은 상부보다도 2.5~7.5초 빠릅니다.

지상 아파트형 두 접근축의 가변 주차 후보14면을 `N=0~14`, 결정론적
배치4종×화재동 전면3점으로 스윕한 결과는 다음과 같습니다.

| 적치 설계 | 전 조건 7분 이내 최대 N | 첫 시간 초과 | 첫 적치 부족 | N=9 최악 | N=10 최악 |
|---|---:|---:|---:|---:|---:|
| 고정 5면 | 9대(64.3%) | 10대 | 12대 | 262.5초 | 445.0초 |
| 확장 14면 | 9대(64.3%) | 10대 | 없음 | 262.5초 | 422.5초 |

확장14면은 추가 적치 위치가 이동거리도 바꾸는 별도 설계안입니다. 이 임계값은
합성 아파트형과 대표 화재3점에 대한 결과이며 실제 도면 전체의 보장값이 아닙니다.

8동 합성 단지(서문+동문, Stanley 1m/s 프로파일)는 가변 차량 `N=0~22` 스윕에서
**연속 8동 7분 안전 최대 N=15**(최악 108동 350.0초)입니다. 다만 이 15는
누적 기준 배치 하나의 임계입니다 — 시드 배치 12종의 강건성 스윕
(`v2complexrobust`)에서 N=15 통과율은 **58%(7/12)** 이고 3개 배치는
N=13에서도 실패해, **배치 강건 임계는 13 미만**입니다. 안전 밀도는 대수
N만이 아니라 차량이 "어디에" 서 있는가에 좌우되며, 이것이 정적 임계 대신
현재 배치를 실시간 재계산하는 관제보드가 필요한 이유입니다. 이 정적 임계를
t=0 교란(쓰러진 나무 2셀 봉쇄 26곳·운송 유닛 감소)으로 다시 시험한 회복탄력성
결과는 다음과 같습니다 (`v2disturb`).

| 교란 | 결과 |
|---|---|
| 도로 봉쇄 26곳 | 안전 유지 25 · 시간 초과 1(동측 종축 남단, 104동 430.0초) · 접근 불능 0 |
| 서측 중앙로 봉쇄 | 8동 전부 우회 성공, 최악 350.0→402.5초 (경로 전환 3동) |
| 운송 유닛 3조(1대 고장) | **즉시 초과** — 103동 455.0초 |
| 운송 유닛 1조 | 570.0초 |

정적 안전 밀도 N=15는 나무 1건은 대부분 견디지만 **유닛 1대 고장만으로
무너집니다** — 회복탄력성의 지배 제약은 도로 여유가 아니라 유닛 여유(4조 전제)이며,
상시 가용 유닛 수가 관제 지표여야 하는 이유입니다.

실제 단지 검증(`v2site`)으로 합성 결과의 적용 한계도 쟀습니다. 지하주차장이
없고 이중주차가 일상인 1970년대 준공 대단지(익명화 — "실제 단지 A")의 정형
판상 2×2동 블록을 공개 자료 기반으로 격자화하면, 골목 도로 5m는 폭3(7.5m)에
미달해 **이중주차 0대에서도 연석 주차열 이동(9대) 없이는 개통이 불가능**하고,
유닛 4조에서도 원단 동이 770.0초(7분의 1.8배)로 초과합니다 — 안전 밀도 N이
존재하지 않습니다(발췌·절단 근사라 절대값이 아닌 합성 단지 대비 상대 비교).

원인 후보였던 "적치 편중"은 반사실 실험(`v2sitestaging`)이 **기각**했습니다.
적치를 동측에 분산해도(면수 동일) 745.0초로 3.2% 단축에 그치고, 6면을
늘려도 개선되지 않습니다. 로봇-틱 직접 계측(`v2util`)이 진짜 병목을
가립니다: 유효 병렬성은 3.25/4조·대기 0.8%로 유닛들은 건강하게 병렬
가동 중이며, 시간을 먹는 것은 **이동 물량 그 자체**입니다 — 골목 폭 5m
때문에 항상 연석 차량 9대를 옮겨야 하고, 4조가 나누면 임계 유닛이
3미션 × 서비스 150초 = 450초를 피할 수 없습니다. 서비스 시간은 어떤 적치
배치로도 줄지 않으므로, **유일하게 유효한 처방은 이동 물량을 없애는 것**
— 접근축의 간선 재지정 또는 구조적 확폭 — 입니다. 직관적 처방(분산 적치)을
기각하고 병목의 본질을 계측으로 특정한 것이 실단지 검증의 결론입니다.

그 처방은 반사실로 실증했습니다(`v2sitezone`). 전용구역을 동 전면 골목에서
**중앙 간선(10m)변으로 재지정**하면 — 같은 단지·같은 만차·같은 4조에서 —
폭3 경로가 골목을 지나지 않아 이중주차 0~8대 구간은 **이동 0대·즉시 개통**,
9~12대 구간도 187.5~250.0초로 **전 밀도 4동 안전(12/12)** 이 됩니다.
골목 기준선의 770초(안전 밀도 없음)와의 대비가 "전용구역 위치 + 전면
주차금지 집행"이라는 실행 가능한 처방의 정량 근거입니다(간선변 전용구역의
소방 활동 타당성은 별도 검토 필요).

배터리·핸드오버 실측(`v2battery`, 만충 = 합성 4시간 기준)이 이를 정량화합니다.
사건당 유닛 최대 소모는 만충의 2.4~4.0%로 **배터리 용량이 아니라 충전 이탈이
문제**입니다: 동시 충전 1대 = 상시 3조 = 8동 중 103동 455.0초 실패. 저전량
유닛 1대가 발생하면 미션 경계 퇴역 + 잔여 재계획(보수적 전면 동기화)으로
103동 기준 322.5→587.5초(+265.0초)가 됩니다. 처방: **예비 유닛 1대(5조 보유,
상시 4조 가용)와 사건 중 충전 금지**가 밀도 N=15의 전제 조건입니다.

## 실행

```powershell
dotnet build ConsoleSim
$env:DOTNET_ROLL_FORWARD='Major'
dotnet run --project ConsoleSim --no-build -- v2test
```

주요 명령:

- `v2switch` — 핵심 스위치(α↔확보시간 교환비 + 봉투 대비 실측) 1장 `output/v2_core_switch.md` 생성
- `v2report` — 핵심 조건을 재계산해 `output/v2_report.md` 생성
- `v2final` — 동일 지상형 맵의 4정책×현실속도 최종 비교 CSV 생성
- `v2density` — 지상형 차량수15×배치4×화재3×적치2의 360조건 밀도 CSV 생성
- `v2disturb` — 8동 단지 N=15에서 t=0 교란(도로 봉쇄 나무·유닛 감소) 회복탄력성 스윕 CSV 생성
- `v2battery` — 배터리 회계·저전량 퇴역·핸드오버 재계획 실측 + 충전 정책 표 CSV 생성
- `v2finegrid` — 레인×5m 전 거리 60점 및 시간 민감도 CSV 생성
- `v2orobots` — 운영 규모 로봇1/2/4/8조 비교
- `v2pockets` — 포켓 개수 스윕
- `v2pocketlayouts` — 포켓 위치 오프셋 민감도

Unity는 `ParkingSim` 프로젝트를 열고 Play합니다.

- 바닥 셀 클릭: 해당 셀을 화재 위치로 삼아 폭 3셀 접근 후보를 자동 생성하고
  물리 개통시간이 가장 짧은 경로로 즉시 재계획
- 봉쇄 배치 모드: 조작 패널에서 켠 뒤 도로 셀 클릭 → 쓰러진 나무(적갈 표시)
  배치/재클릭 해제 → 자동 재계획으로 우회 경로 재생. 보호 셀(진입구·전용구역
  접근셀·주차면)은 배치가 거부되고 사유가 표시되며, 관제보드도 봉쇄 조건을
  반영해 "교란 하 동별 대응력"으로 재계산
- 관제모드: 직교 탑뷰에서 모든 후보·선택 경로와 분석용 격자를 표시
- 관제보드(우측 하단 상시 패널): 현재 밀도·진입구·가용 유닛 조건으로 8개 동
  전수의 예상 개통시간을 백그라운드 재계산해 동별 5/7/9분 색상으로 표시 —
  "지금 불나면 몇 분 만에 열리나"를 화재 발생 전에 상시 확인
- 가용 운송 유닛 4/3/2/1조 선택(조작 패널): 충전·고장 이탈을 가정한 재계획과
  관제보드 재계산에 함께 반영 — 3조 선택 시 103동이 7분 초과로 바뀌는 것이
  S1·S2 실측의 화면 재현
- 3D모드: 등각 원근에서 선택 경로와 아파트 환경만 표시
- 청록색: 선택 경로, 파란색: 선택되지 않은 상위 후보, 빨간색: 화재 위치
- 숫자키 `1`: 기본 화재 위치의 전면 5대 재배치 기준선
- 숫자키 `2`: 현재 화재 위치의 자동 핵심경로
- `` ` `` (백틱): 관제모드와 3D모드 전환 (조작 패널 버튼과 동일), `Space`: 일시정지/재생,
  `R`: 현재 계획 처음부터 재생
- 3D모드에서 이동 대상 차량은 상공의 회전 플럼밥 마커로 표시 (주황=대기,
  청록=운반 중)
- 운송유닛의 노란 상태등과 차량 상승은 차량 취득90초 진행, 초록 상태등은
  차량 해제60초 진행을 뜻하며 HUD에 서비스 종류·진행률을 표시
- 접근로 종점의 화재동과 북쪽 배경동은 층별 창호·출입구가 있는 코드 생성
  아파트 외형이며, 콜라이더가 없는 시각 전용 객체라 계획·클릭 판정에 불개입
- HUD 시간은 Stanley 공개사양의 1m/s·pickup 90초·release 60초 참조 프로파일
  기준이며, 후보 생성 실패 시 기존의 성공한 재생 화면을 유지하고 실패 이유를 표시

커스텀 모델은 아래 `Resources` 경로에 GameObject/프리팹으로 추가하면
런타임 primitive 폴백을 자동 대체합니다. 모델은 로컬 `+X` 방향을 전면으로 하고
Unity 1m 단위를 기준으로 맞춥니다.

- `Assets/Resources/ParkingSim/Vehicles/Car`
- `Assets/Resources/ParkingSim/Vehicles/TransportUnit`
- `Assets/Resources/ParkingSim/Environment/Apartment`

차량·운송유닛은 공유 동적 루트, 후보·분석 격자는 관제 루트, 아파트·발표용
바닥은 3D 루트에 생성됩니다. 모드 전환은 Core 계획이나 재생 틱을 초기화하지 않습니다.
현재 운송유닛은 `real_v7` 물류로봇의 하판 렌더러 15개만 정리한 시각 전용
프리팹을 사용합니다. ROS2·센서·카메라·물리 컴포넌트는 포함하지 않으며,
본체 높이는 약 0.08, 리프트 플레이트 상단은 약 0.09인 저상형 표현이며,
원본 출처와 재배포 전 라이선스 확인 사항은
`Assets/Imported/real_v7/SOURCE.md`에 기록했습니다.

## 한계

- 합성 격자이며 실제 아파트 도면을 아직 사용하지 않습니다.
- 연속 공간의 차량 회전 swept volume, 실제 센서·제어·가감속은 모델 밖입니다.
- 절대시간은 셀당 시간 가정에 종속됩니다.
- 운영 규모 결과는 후보8의 실행 가능한 상한이지 전역 최적값 증명이 아닙니다.
- 실제 적용에는 성능위주설계 검토와 실증이 필요합니다.
